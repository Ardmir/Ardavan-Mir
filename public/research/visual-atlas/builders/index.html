05 · Builder Structure Archetypes

Five ways to arrange the same recurring pieces.

The difference is not simply visual styling. Each arrangement changes what users inspect, what they manipulate, and what counts as evidence that the build is working.

01

Structural model

Prompt ↔ Artifact

AI / intent↔live artifact↔code / design
What dominates
A split workspace in which conversation and the running thing stay visible together.
Where AI lives
AI operates through the artifact, but users can increasingly select, design, or edit directly.
Direct manipulation
The rendered app, selected UI elements, or source code.

What this teaches usThe artifact becomes a first-class partner to the conversation—not merely its final output.

02

Structural model

IDE + Agent

files↔editor↔agent+ terminal / browser
What dominates
A familiar repository and editor, expanded with agent and verification surfaces.
Where AI lives
AI is contextual to files, diffs, terminal state, previews, and longer-running tasks.
Direct manipulation
Code, files, diffs, commands, and sometimes agent artifacts.

What this teaches usTrust shifts toward inspectable changes and execution evidence, not just a convincing preview.

03

Structural model

Canvas + AI

resources→visual canvas↔properties / AI
What dominates
The artifact itself—or a spatial composition of components—is the primary work surface.
Where AI lives
AI generates or alters objects that remain available for direct spatial manipulation.
Direct manipulation
Screens, components, layout, properties, and data bindings.

What this teaches usA visual object model gives users control without requiring the generated artifact to collapse into code.

04

Structural model

Workflow / Graph

trigger / input→connected nodes→output+ run trace
What dominates
An executable graph makes sequence, branching, dependencies, and tool use visible.
Where AI lives
AI may create the graph, configure a node, or appear as one capability inside the graph.
Direct manipulation
Nodes, edges, parameters, variables, and step outputs.

What this teaches usThe representation doubles as explanation: execution can be inspected where the system was composed.

05

Structural model

Capability Studio

models / media / tools→prompt studio→sample app / code
What dominates
A capability palette and playground lead users from model behavior to an application.
Where AI lives
The model is both the material being explored and the engine helping compose the result.
Direct manipulation
Prompts, model settings, multimodal inputs, code, and starter applications.

What this teaches usFor AI-native apps, model capability discovery can be the front door to building—not a supporting settings panel.

06 · Anatomy of an AI Builder

One loop. Several representations.

At category level, the most stable structure is not a specific screen layout. It is a loop that keeps intent, a manipulable representation, runtime evidence, and release close enough to support iteration.

Variable

Emerging

Still taking shape

Agent managers, background task systems, artifact-based review, and browser-recorded verification.

Structural questions to carry forward

  1. What should be the primary manipulable representation?
  2. How close should AI, direct editing, and runtime evidence remain?
  3. When does a builder need a managerial layer above the creation surface?
  4. Which supporting resources deserve persistent regions versus contextual access?
  5. What form of review best supports correction before release?
